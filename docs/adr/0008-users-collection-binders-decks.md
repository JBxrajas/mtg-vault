# ADR 0008 — Users, collection, binders and decks

**Status:** accepted

## Context
Phase 3 needs accounts and the core data: what a user owns (including several printings of the same card), how to organize it, and decks. Requirements from the product owner:

- A user has **one** collection and **many** decks.
- The collection is an inventory that distinguishes printings (set, collector number), finish, condition and language.
- **Binders** are sub-collections of the single collection.
- Decks have a **format** and their cards are **divided by card type** (creature, sorcery, instant, enchantment, artifact, …).
- Login is basic for now: **username and password**.

## Decision

### Users and login
Better Auth ([ADR 0004](0004-hono-api-and-better-auth.md)) with email-and-password enabled and the **username plugin**: people sign up and sign in with a username and a password. Its tables (`user`, `session`, `account`, `verification`) live in our own Postgres (`packages/db/src/auth-schema.ts`, generated by Better Auth's CLI and kept as generated).

Better Auth's core `user` table requires a unique `email`. Username-only sign-up therefore fills it with a synthetic address (`<username>@users.invalid`, a reserved domain that never receives mail). Consequences: no email verification and no password reset by email yet; adding a real optional email later is a normal profile update. The username plugin is not wired into the API yet; only the tables exist.

### Collection and inventory
- `collections`: one row per user (`user_id` is unique).
- `collection_items`: the inventory. One row is a **stack** of identical cards, identified by `(collection, printing, finish, condition, language)`; that combination is unique, so adding the same card again increases `quantity` instead of creating a duplicate row. Different prints of one card, or the same print in foil and non-foil, are different rows. Also stores purchase price, acquisition date and notes.
- `finish` is `nonfoil | foil | etched`, matching the finishes Scryfall lists for a printing. This replaces the earlier `foil` boolean in the shared schema.

### Binders (sub-collections)
- `binders`: named groups inside the collection (a physical binder, a box, a trade list). Names are unique per collection.
- `binder_items`: how many copies of an inventory stack sit in a binder. Because a stack can be split (2 copies in one binder, 1 in another), this is a join table with its own `quantity`. The rule "copies across binders never exceed the stack's quantity" is enforced by the API, not by the database. Cards not in any binder are simply in the general collection.

### Decks
- `decks`: owned by a user (many per user), with `name`, `format`, `description` and `is_public`.
- Formats (`deckFormatSchema` in `packages/shared`): standard, pioneer, modern, legacy, vintage, commander, oathbreaker, brawl, pauper, historic, casual. Stored as text and validated with Zod, so adding a format needs no migration. Format rules (deck size, copy limits, legality) are not enforced yet.
- `deck_cards`: a card in a deck, keyed by `(deck, oracle card, board)`. `board` is `main | sideboard | maybeboard | commander`. A deck lists **oracle cards**, not printings (an optional `printing_id` picks the art to show), and is independent of what the user owns. "Cards I own / missing" is a comparison by oracle id against the inventory, computed on read.
- **Type groups are derived, not stored.** `cardCategory(typeLine)` and `groupByCategory` in `packages/shared` read `cards.type_line` and return the display groups in this order: Commander, Planeswalker, Creature, Sorcery, Instant, Artifact, Enchantment, Battle, Land, Other. A card with several types goes to one group by priority: Land, Creature, Planeswalker, Battle, Instant, Sorcery, Artifact, Enchantment (so an Artifact Creature is a Creature and an Artifact Land is a Land). Only the front face of a double-faced card counts. Sideboard and maybeboard are listed separately and not grouped.

## Consequences
- One source of truth for types (`type_line`), so groups never go stale after a catalog re-import.
- Deleting a user cascades to their sessions, accounts, collection (items, binders), and decks.
- The database enforces: one collection per user, no duplicate stacks, positive quantities, no duplicate card per deck board. The binder quantity rule and format rules live in the API.
- Without a real email there is no password recovery; this is accepted for the basic first version.
- Migration `0002` creates all of this. It was verified on a throwaway Neon branch (constraints and cascades), not yet applied to `production`.
